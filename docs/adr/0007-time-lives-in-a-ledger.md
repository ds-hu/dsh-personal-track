# 时间不住在别的记录里：一张按天的时间账本

两个症状，一个原因。

**删掉一条待办**，它上面的 40 分钟专注就没了——从时间视图的专注行、从「累计专注」，还从**对话**里被重新算回来（专注是对话里的洞，洞随条目一起消失，那段对话时间反而变长）。因为专注会话是条目记录里的一个字段：条目的生命周期变成了时间的生命周期。

**presence 一天约 200 KB**，一年 73 MB，而备份导入的请求体卡在 16 MB：导得出来、导不回去。实测 44% 的字节是 `in`、43% 是 `out`，闭合段中位 7–10 秒——四成不到 5 秒的抖动被 3 分钟桥接在读时并成一段，存下来的细节比信息多。

两个都是「一段已经发生的时间」，都只需要 `{主体, 开始, 结束}`。一个住在会被删掉的东西里，一个住在会老去的东西里。

- **Status**: accepted
- **Considered Options**
  - **专注会话单独一张退役表**（删除时复制过去）—— 已实现又撤回：它只解决一半，而「一段已关闭的时间」因此有了两个定义、两个读入口、备份里两个数组，三天窗口那条规则也只写在 presence 一侧。
  - **软删除**（条目留 `deletedAt`）—— 否决：与「登记硬删除」相反，且每一条读路径都要记得过滤，还需要一个真正的删除出口。
  - **所有专注会话都住进账本，条目只做视图**—— 否决：条目的读是「这条上花了多久」，账本的键是日子；那样每次 `view()` 都要扫遍所有日子，或者维护一份会漂移的反向索引（ADR 0003 拒绝的正是第二份关系）。
  - **账本 + 三天原始窗口**（采纳）：关闭的区间进账本，原始事件只留三天，两条路写同一种行。
- **Consequences**
  - `time/<习惯日>` 一天一个文档，`items` 是三种行之一：`focus`（被删条目的一段专注，带删除那一刻的标题快照）、`talk`（一段对话停留）、`prompt`（一个提示时刻，2 分钟尾随仍在读时算）。
  - **两个写者，两个读者**：删除条目写 `focus`；日子过了三天把原始事件折成 `talk`/`prompt` 并删掉原始文档。时间视图读「当天账本 + 最近三天原始事件」，「累计专注」读「现存条目 + 账本」。
  - **不写注意力模型**：2 分钟尾随、3 分钟桥接、巡逻、专注扣减仍在 `attention.ts` 里算。折出来的是观察（一段停留），不是判断。
  - **id 是确定性**的（专注会话自己的 id、`talk:<session>:<start>`、`prompt:<session>:<at>`）：一次重试的删除、一次中断在两写之间的压缩，都不会让同一段出现两次。
  - **先写后删**：删除条目先写账本再删记录；压缩先写账本再删原始事件。中间崩溃留下的重复由 id 去重逢上——per-record 后端没有事务，这是它能给的。
  - 域版本**不升**：新表 additive，旧构建不声明它也就不会丢弃它（与 `presence` 相同）。备份**升到 v6**：新增 `time` 数组，旧 reader 会在下一次导出时静默 strip 掉它，所以必须靠版本拦住。
  - **收益是文件**：presence 原始数据从一天 200 KB 变成三天固定约 600 KB，之后每天约 31 KB（实测折叠 4.8×）；16 MB 的导入上限从「约 80 天」推到「一年多」。
  - **左栏「专注过」仍不收退役条目**：那条派生行是给仍在的条目用的（标题是按钮，点开进专注模式）。要在左栏看见它，得另加一条 wire 字段——那是一次显示决定，不是这次的数据决定。
